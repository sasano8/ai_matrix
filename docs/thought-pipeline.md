# 思考パイプライン構想

状態：構想・今後の実装要件。ここに記載するパイプラインやファイル保持は、現行アプリにはまだ実装されていない。

## 目指す体験

ひとつの投稿を展開するマトリクスから、複数の工程を行き来して考えを育てる「思考パイプライン」へ発展させたい。マトリクスは廃止せず、それぞれの工程で考えるための成果物として使う。

AI が結論を決めるのではなく、本人が考え、編集し、次へ渡す内容を決められることを大切にする。生成方法は問いかけに固定せず、工程ごとにプロンプトを選択・編集できるようにする。

## 工程と引き継ぎ

ユーザーが挙げた工程は「問いかけ・要件定義・設計・テスト・運用・受入テスト」。工程名、順序、追加・省略は変更できる設計を目指す。

初期テンプレート案は次の順序。確定仕様ではない。

```text
問いかけ → 要件定義 → 設計 → テスト → 受入テスト → 運用
```

受入条件は要件定義中にも検討できるようにする。工程を一方向に消化するだけでなく、前工程への戻り、別案への分岐、再展開も扱いたい。

各工程は次の内容を保持する。

- 入力：投稿文、前工程からの引き継ぎ、参照ファイル。
- 展開：観点と深掘りからなるマトリクス、編集内容、自分の考え。
- 引き継ぎ：次工程へ渡すために本人が確認・編集したまとめ。
- 生成設定：選択・編集したプロンプト、観点・深掘りレベル。

「次へ引き継ぐ」では、現在の工程から次工程向けの入力案を作り、本人が編集・確定した後に次のマトリクスを展開する。単なる短縮要約ではなく、目的、背景、決定事項と理由、未解決の問い、前提、扱わない範囲、受入条件、参照資料など、次工程に必要な情報を残す。

元の入力・マトリクス・まとめは別々に保持する。まとめを作っても、元の思考やファイルを置き換えない。

## 成果物から前提を見直す

成果物から入力へのフィードバック、いわば「逆展開」も行いたい。操作名の案は「前提を見直す」。

例：設計を展開して実現上の問題に気づいたら、要件定義へ確認事項や変更候補を返す。テストを考えて成功条件が曖昧だと分かったら、その根拠とともに問いを前工程へ返す。

元の入力を正確に復元する操作ではなく、成果物を成立させるために必要な前提を問い直す操作として扱う。

- どの成果物・カードを根拠に、どの入力・工程へ返すのかを記録する。
- 矛盾、不足情報、確認したい前提、修正候補を示す。
- 元の入力や確定事項は自動的に書き換えない。
- 本人が採用・編集・保留・却下を選べるようにする。
- 前工程の変更後も後工程を無断で再生成せず、影響の確認と再展開を選べるようにする。

## 入力としてファイルを保持する

テキスト投稿だけでなく、資料などのファイルを工程の入力として取り込み、後から開いたり、次工程でも参照したりしたい。ファイル名だけを表示するのではなく、選択したファイル本体を保持する。

必要な振る舞い：

- ファイルの追加、一覧表示、再ダウンロード、参照の解除ができる。
- ファイル名、種類、サイズ、取り込み日時、参照元の工程を確認できる。
- リロード・タブの再起動後も、同じブラウザでファイル本体と工程との関連を復元できる。
- 元ファイルと、AI 入力用に取り出したテキスト・抜粋を分けて保持する。
- 次工程には参照を引き継ぎ、同じファイル本体を毎回複製しない。
- どのファイル・版・抜粋を生成に使ったかを記録する。
- 保持することと、全文を AI に渡すことを分ける。今回使う資料と範囲を本人が確認できる。
- 読み取れない形式も保管は可能にし、「保持済み」と「AI が内容を読めた」を区別する。
- 容量不足や保存失敗を表示し、未保存のものを保存済みとは表示しない。

保存方式の案は **IndexedDB に Blob とメタデータを保存する**こと。現行の localStorage は文字列の保存であり、添付ファイル本体や増えていく工程の保存にはそのまま使わない。将来の移行では既存のマトリクスを保持し、移行成功を確認するまで旧データを削除しない。

最初の内容取り込み対象の案は、テキスト・Markdown・CSV・JSON。PDF・画像などの内容解析は別途、ブラウザやモデルの対応を確認して追加する。対応形式、サイズ上限、抽出・分割方法は実装時に決める。モデルの入力上限を超える資料を黙って切り捨てず、抜粋・分割する範囲を明示する。

フロントエンドだけで扱う方針を維持し、取り込んだファイルをアプリから外部サーバーへ自動送信しない。端末間同期は別機能として扱う。ブラウザ保存はサイトデータ削除・ストレージの退避などで失われうるため、パイプラインと添付資料のエクスポート／インポートも検討する。

## データモデルの案

工程をノード、引き継ぎ・フィードバックをエッジにするグラフと、マトリクス内の観点・カードの構造を組み合わせる。次は概念モデルであり、実装済みの型やスキーマではない。

| 要素 | 保持する情報 |
| --- | --- |
| Pipeline | ID、名前、工程ID一覧、初期の表示順 |
| Stage | ID、工程名、入力の版、マトリクスの版、プロンプト・レベル、状態 |
| Matrix | ID、話題、観点、カード、編集内容、自分の考え |
| Handoff | 元工程と参照版、次工程、確定した引き継ぎ文、添付参照、作成日時 |
| Feedback | 発生元の成果物と版、返す先の工程・入力、根拠、見直し候補、採用状態 |
| Attachment | ID、元ファイルの Blob、ファイル名、MIME、サイズ、取り込み日時、版 |
| AttachmentReference | ファイルIDと版、参照する工程、抽出テキスト・使用範囲 |

次工程が「どの時点の入力・まとめ・ファイル」を使ったかをスナップショットとして残す。元の工程を編集したら、既存の後工程には「入力元が更新された」ことを表示できるようにする。単に現在の値を参照するだけにして、生成時の根拠が後から変わってしまう設計は避ける。

以前に話した「カードの中に別のマトリクスを開く」構想も、このモデルと両立させたい。子マトリクスへの関係、次工程への引き継ぎ、前工程へのフィードバックは、意味の違う関係として区別する。

## 画面と操作の案

上部に工程の一覧を置き、選択した工程の入力・マトリクス・詳細ページを表示する。投稿や資料を主役にし、生成設定は必要なときに開く。今のコンパクトな見出し表示と、広い詳細・編集ページを生かす。

- 「深掘りする」：現在の工程で、同じ観点を掘り下げる。
- 「視野を広げる」：現在の工程に、新しい観点を加える。
- 「次へ引き継ぐ」：まとめを確認・編集し、次工程を展開する。
- 「前提を見直す」：成果物から、入力や前工程への見直し候補を作る。

奥行きのある遷移や3Dの全体表示は検討対象とするが、必須ではない。文章の読み書き、現在の工程、戻る場所が分かることを優先する。

## 実装の進め方の案

1. 複数工程・入力・マトリクスを失わず保存し、行き来できるようにする。
2. ファイル本体と参照を保存し、対応形式のテキストを入力に使えるようにする。
3. 確認・編集を挟んだ工程間の引き継ぎを作る。
4. 成果物から前提を見直し、本人の採用操作で反映する流れを作る。
5. 分岐、変更の影響表示、バックアップ、全体表示を拡充する。

これは実装順の提案であり、今回の依頼は構想をリポジトリに残すこと。工程・ファイル保持などの実装完了を意味しない。

## 将来の受入確認

- 工程を進めたり戻ったりしても、元の入力・編集・成果物が残る。
- 確認した引き継ぎ文と資料の参照が、次工程の実際の入力と一致する。
- 前提の見直しを作っただけでは、既存の入力や決定事項が変わらない。
- 入力元の変更と、後工程が参照した過去の版を区別できる。
- ファイルを追加した後にリロードしても、元ファイルを再ダウンロードできる。
- 未対応形式・保存失敗・入力上限を、読取成功や保存完了と取り違えない。
- 既存の localStorage のマトリクスを失わず移行できる。
